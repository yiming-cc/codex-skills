# 科研看板

本 skill 随独立的私有 research-board 仓库分发，也可通过 symlink 安装到用户级目录，从其他科研代码仓库调用。不需要 MCP、飞书或服务器 SSH。

## 严格按用户要求操作

调用本 skill 不等于授权创建任务。先确定用户要求的是创建课题、维护文档、记录进展，还是新增/拆分任务；只执行本次明确要求的操作，不自动扩展相邻工作。

- **创建课题**：配置 project，并按用户提供的内容建立或更新课题说明；不自行添加 todo、任务卡片、里程碑、依赖、负责人或排期。
- **维护文档**：只创建/修改指定文档；文档中的研究方向、设想或“下一步”不自动转换为任务。
- **记录进展**：更新用户指定的现有任务或文档；没有对应任务时，可按要求记入项目文档，不自行补建任务卡片。
- **新增/拆分任务**：只有用户明确要求创建 todo/任务、拆解工作或制定任务计划时，才创建相应任务；数量和范围以请求为限。
- **普通 todo**：用户给出大致描述时，只适度润色标题和 Description，不自行生成 Acceptance Criteria、DoD、子任务或检查清单。要求“新增 todo”不等于要求“拆分 todo”。只有用户提供/明确要求验收项，或明确要求拆分该任务时，才按其指定范围填写；不得另补未经要求的交付物和指标。
- **查询、解释或建议**：只回答问题；除非用户同时要求保存或修改，不写入仓库。

不要为了跟踪本次 skill 操作而创建管理任务，也不要因为上游 CLI 工作流建议使用任务或验收条件，就把用户的描述扩充成任务/验收清单。不要把自行增加的检查项搬进 Description 或改名为 DoD 来绕过此范围。对资料中的事项保留事实与计划的区别；合理推断用于完成已授权的操作，不用于追加交付物。

## 找到共享仓库

使用本 skill 内的 `scripts/board.py`，它会解析 symlink 找到真实 checkout，不依赖当前工作目录：

```bash
python3 <本skill目录>/scripts/board.py root
```

下文 `board` 表示 `python3 <本skill目录>/scripts/board.py`。它只对该共享仓库操作；当前科研代码仍在当前工程中工作。不要把实验代码、数据集或模型权重复制进看板仓库。

先读取看板仓库的 `AGENTS.md`、`backlog.config.yml` 和 `board.json`。若缺少依赖，在看板仓库运行 `npm ci`。原生 CLI 的用法以 `board backlog <command> --help` 和 `board backlog instructions overview` 为准。

## 同步与定位

- 仓库干净且在 main 时，执行 `board sync`。有未提交修改时先检查，保留原有工作；不要 stash/reset 后假装已同步。
- 查询现有任务与文档，优先更新对应记录，避免同一个实验每次都新建任务：`board backlog task list --json`，`board backlog search "关键词"`。
- 从当前代码仓库提取真实的仓库地址、commit、配置路径、运行 ID、结果文件或论文修改位置。不能把本机绝对路径当成所有成员都能访问的成果链接。

## 写任务和文档

- 用户要求创建课题时配置 project：`board project-add "课题名称"`；文档可用同名 tag 和子目录归类，到此即可，不附带任务拆分。
- **仅在用户明确要求创建任务时**，填写 `--project`、标题和基于用户原意的 Description；默认不传 `--ac` 或 `--dod`。负责人按下节成员池匹配；新任务未指定负责人则保持未分配，更新已有任务时不擅自改负责人。
- 状态是 `To Do`、`In Progress`、`Review`、`Done`。按实际进展与用户确认的完成状态记录；存在用户指定验收项时按其核对，没有验收项时不为改变状态而补写。阻塞使用 `blocked` 标签并说明原因。
- 使用 CLI 修改元数据、验收条件、依赖和结构化任务章节，不手工重编号或猜测内部格式。进展用 `--append-notes` 追加；讨论用 `--comment` 和 `--comment-author`；完成摘要用 `--final-summary`。不要用 `--notes` 意外覆盖历史。
- 进展说明：做了什么、观察到什么、证据在哪里、下一步、阻塞。结果未确认要写“未核验”，没有开展的工作不写成已完成。不凭 commit 数或运行时长猜百分比。
- 项目说明、实验报告、会议记录、阶段总结使用 `backlog doc create` 和 `doc update`。长正文可写入临时 Markdown，再用 `board doc-write DOC-ID /path/to/body.md` 导入，避免 shell 转义损坏内容。
- 决策记录说明上下文、选择、理由和影响。只有用户已作出决定时才记录为已决策。
- 常用命令和科研记录格式见 [工作流示例](references/workflow.md)，按当前任务需要读取。

## 指定负责人

仓库根目录的 [members.json](../../../members.json) 是成员名单的唯一来源。它保存固定 `id`、显示姓名 `name` 和用户确认的 `aliases`；ID 不代表 GitHub 账号。

- 指定或更换负责人前，执行 `board members "用户给出的姓名或ID"`，从结果取 `name` 传给原生 CLI 的 `--assignee`。多个负责人逐一匹配，再按 CLI 支持的方式传入；清空负责人用 `--assignee ""`。
- 只匹配名单中的完整姓名、固定 ID 或已登记别名；不做模糊猜测，不从 Git 作者、当前登录身份或“我”推定负责人。无法唯一匹配时，先完成不依赖该身份的部分，再询问。
- 只有用户要求添加成员或确认别名时才修改名单，不自动新增姓名/账号映射。别名不得与其他成员的姓名、ID 或别名冲突；已有 ID 保持稳定。
- 只要求分配负责人时只改负责人，不顺带改变任务状态。`board check` / 发布校验会拦截当前任务和草稿中未使用名单规范姓名的负责人；归档记录保留历史身份。

## 发布

用户要求“同步/发布/更新到共享看板”时，可以提交这次范围的记录并推送；仅“起草/看看/制定建议”先留在本地。已有明确授权继续适用。

1. 检查 diff，运行 `board check`，确认没有重复编号、无效项目和悬空/循环依赖。
2. 用 `board publish --message "具体进展" --path backlog/tasks/实际文件.md --path ...` 提交明确选择的记录；新增项目时包含 `--path backlog.config.yml`，更新成员池时包含 `--path members.json`。命令仅支持 main，保留其他范围修改，正常 rebase 后再次校验，再 push。该 helper 不发布 skill/脚本；用户要求修改这些文件时，用普通 Git 仅提交本次相关文件，经校验和正常 rebase 后推送。
3. 遇到编号冲突、语义不明的合并冲突或推送失败时，保留现场并说明，不 force push 或静默覆盖。修编号必须检查相关依赖和文档引用。
4. 报告任务 ID、变化、commit，以及 `board.json` 中的网站地址。服务器约每分钟检查一次 main；要确认线上版本时执行 `board status`，比较 `commit` 与 `git rev-parse HEAD`。未显示新 commit 时说明仍在同步，不声称已上线。

公共网页无需登录、内容只读。不要通过公网网页写入记录；实际写入使用本地仓库与 Git 权限。
